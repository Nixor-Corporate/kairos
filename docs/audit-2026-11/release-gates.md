# Release gates

All gates are open until the named owner records evidence against the reviewed release SHA. Store sensitive incident evidence in the restricted incident record. Link to it from the release record without copying credentials or personal data.

| Gate | Owner | Action | Evidence required to close |
| --- | --- | --- | --- |
| SEC-01 · Containment | Security and infrastructure owners | Keep Actions disabled. Preserve workflow, audit and host evidence. Inventory identities, runner access, developer checkouts, deployment credentials and systems reachable during the incident window. Investigate affected workstations from a clean machine. | Incident owner signs off on affected systems, outstanding gaps and containment. A private evidence inventory lists retention, custodians and the relevant run IDs. |
| SEC-01 · Rotation and provenance | Identity, hosting and repository owners | Revoke or rotate potentially exposed GitHub, SSH, hosting, database, relay and Google credentials from clean systems. Invalidate affected sessions. Compare the deployed webroot, relay and scheduled jobs with a reviewed build from the clean commit. | Rotation records confirm old credentials were revoked, clean identities were used, and services reconnect with replacements. Approved artifact hashes match observed files or have an explained exception. |
| SEC-04 · Default branch | Repository owner | Require reviewed pull requests for the default branch. Restrict direct pushes, force pushes, deletion and bypass actors. Assign review ownership for workflows, dependencies and deployment files. While Actions is disabled, attach reviewed offline test evidence to the release record. | Export or screenshot of effective rules for the actual default branch, documented bypass list and reviewer ownership. Reopening CI requires a separate security review and authorization. |
| SEC-05 · Canonical HTTPS | Cloudflare and cPanel owners | Trace redirects at the edge and origin. Verify proxy scheme propagation and define one canonical HTTPS URL. Align the application base path, permitted origin, Google configuration, session cookie path and hostname with the chosen URL. | Browser and GET/HEAD traces from HTTP and HTTPS on both root and `/signoff/` show an HTTPS final destination without downgrade or loops. Real staging Google and local sign-in survive reload and normal reopen. Secure session cookies reach the intended endpoints, logout invalidates the session, and the relay uses WSS. |
| SEC-06 / SEC-07 · Relay | Application and infrastructure owners | Confirm revocation behavior after course removal, account disable and session expiry. Verify broker access and process isolation. Record remediation or a time-bounded risk decision with compensating controls. | Staging role-change and reconnect evidence, host access review, and named owner for any residual risk. |

## SEC-01 · Incident containment and provenance

**Open.** The original run inventory records 58 executions including 18 successful runs of Security Audit. On November 16 the 104 advertised refs all resolved to locally available objects and none of their tips contained the known incident paths. Historical references remain reachable. Rotation, actual exposure, developer workstations, cPanel and deployed artifacts require owner evidence. [Incident investigation](security.md)

1. From a known-clean workstation, the incident lead preserves GitHub run and job metadata, repository and organization audit logs, runner information, affected checkouts, cPanel login and deployment logs, cron and relay configuration, and current asset manifests in the restricted case. Record collection time, custodian, SHA-256 and retention. Treat the historical automation and editor files as evidence.
2. The identity, GitHub, cPanel and Google owners inventory accounts and credential classes reachable during the run window. Revoke old credentials and sessions, rotate affected developer and deploy tokens/SSH keys, hosting, database, relay, OAuth and Drive credentials, and reconnect through clean identities. Record old credential fingerprints or IDs, revocation and service verification timestamps. Escalate missing logs or inaccessible endpoints to the incident lead.
3. The hosting owner exports a read-only manifest of deployed app assets, PHP dependencies, relay files and scheduled jobs. A second reviewer compares SHA-256 values against an offline build from the reviewed SHA and audited lock/pin inputs. Check untracked files and unexpected jobs and keep the verified rollback artifact with the case. The incident lead records exposure disposition, checked hosts, rotations and artifact comparison before closing this gate.

## SEC-04 · Default branch protection

**Open.** On November 16 `main` reported `protected: false` and its effective branch rules endpoint returned an empty list. Repository Actions stayed disabled. Default workflow token permission was read and automated PR approval was disabled.

1. The repository owner opens **Settings → Rules → Rulesets**, targets the actual default branch, and activates a rule requiring a pull request, reviewer approval, code-owner review for security-sensitive paths, dismissal of stale approvals, approval of the most recent reviewable push, and resolved conversations. Block force pushes and deletion. Enforce the PR rule on administrators. Use an empty bypass list or a named incident emergency group with access reviewed by the org owner. Assign owners to workflows, dependency inputs and deployment paths after reviewing the ownership file. [GitHub ruleset controls](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
2. While Actions stays disabled, attach the independent offline lint, PHP/Node and SQL/HTTP fixtures, and dependency/supply-chain review for the exact PR SHA. If an approved external check app exists, require its scoped checks and bind them to that app. Otherwise, gate merging through the independent review evidence and add required lint, authorization/queue, and migration/export checks when a separately approved trusted CI source can report them. Record the active rules, exceptions, effective `main` rules and a protected PR merge check.
3. Actions reactivation requires named security and org owner approval after SEC-01 closes. Audit every workflow entry point and dependency, pin external actions to reviewed full SHAs, allowlist publishers or actions, use default read tokens and the minimum narrow job permissions, and keep untrusted PR jobs away from secrets, write grants and privileged runners. Stage on a clean runner with no production credentials and verify expected check identities before requiring them.

## SEC-05 · Canonical HTTPS

**Open.** Public GET and HEAD of `https://kairos.nixorcorporate.com/signoff/` returned a `302` to `http://kairos.nixorcorporate.com/`. HEAD at either root scheme returned `200`. The record is proxied, the zone SSL mode is Full, Always Use HTTPS is off, and Cloudflare Trace with origin forwarding skipped showed no matching redirect action on either scheme of `/signoff/` or on HTTPS root. The Requests Trace result points to the origin path for differential diagnosis. The tracked `.htaccess` directs `/` to `/signoff/`, which differs from the live response. The exact deployed Apache or application rule requires hosting access. [Public canonical URL](https://kairos.nixorcorporate.com/signoff/)

1. The cPanel owner verifies the domain document root and TLS certificate in **Domains**. From an authorized host, compare the edge with a direct TLS origin request using the same Host/SNI. Use `curl --resolve 'kairos.nixorcorporate.com:443:ORIGIN_IP' -sS -D - -o /dev/null https://kairos.nixorcorporate.com/signoff/` locally, substituting the private origin address. Repeat for `/`, `/signoff`, and `/signoff/api/config.php`, with GET and HEAD. Capture statuses and Location headers only. Use origin access/error logs and temporal correlation to identify the first redirect. Keep origin addresses and private configuration in the operator record.
2. Inspect **Domains → Redirects**, the domain's Force HTTPS setting, the Apache/proxy vhost and both document-root and mounted `.htaccess` files. Check the live document-root files against the verified artifact. Inspect the first PHP handler if the request reaches it. Remove or correct the confirmed downgrade at its source, preserve the path and query when redirecting legacy URLs, and choose one HTTPS `/signoff/` canonical mount. Check trusted proxy scheme propagation and validate the origin certificate before using Full (strict). Do not add a root-to-subpath redirect until the reverse live redirect has been removed. [cPanel Redirects](https://docs.cpanel.net/cpanel/domains/redirects/) · [Cloudflare Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)
3. Stage `APP_ORIGIN`, `PUBLIC_APP_ORIGIN`, `APP_BASE_PATH`, the Google redirect URI if using the redirect flow, allowed origin, secure cookies and WSS on that mount. Prove HTTP upgrades to HTTPS, HTTPS stays secure, routes resolve without loops and legitimate sign-ins, reload/reopen, logout and reconnect work. Save sanitized GET and HEAD traces and browser observations for both host and edge.
