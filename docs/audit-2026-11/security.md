# Security and incident verification

## Incident scope and evidence

The public GitHub repository and local checkout agreed on the `main` commit. `git ls-remote --heads --tags origin` returned 104 heads/tags, with no differences from the local tracking inventory after normalizing names. A tip tree check covered 106 refs including local master and the origin HEAD alias. None contained the six incident paths. History retains them. At the time of review, `git diff --name-status 037de01 5688251` was empty. The post-remediation code tree matches the June 30 merge tree. This is stronger evidence than the commit message for these six tracked paths, and says nothing about deployment files, unadvertised refs, forks, external runner state, workstation artifacts, or downloaded payloads.

Repository Actions were disabled. The current default workflow permission reported read access, and workflow-created PR approvals were disabled. The repository returned zero registered self-hosted runners, repository Actions secrets, variables, deployment keys, environments and recorded deployments. GitHub returned zero effective rules for `main`. The available CLI identity had repository administrative access, and the authenticated token listed `repo` and `workflow` scopes among its grants. Organization-level Actions secrets returned HTTP 403. Current counts cannot establish what existed during the incident. External cPanel/Cloudflare, OAuth, Drive, DB and developer access records still require the corresponding owners.

### Containment and release gate

1. Keep Actions disabled pending review. Preserve Actions run metadata, relevant audit logs, protected copies of historical Git objects, and endpoint telemetry. If a host opened an affected revision, investigate it from a separate trusted machine.
2. Revoke and reissue potentially exposed developer GitHub tokens, OAuth sessions, SSH keys and deployment credentials. Inventory credentials exposed to workflows and developer hosts, including hosting, DB, relay secret and Google service-account credentials where accessible. Coordinate rotation and revocation with affected owners and verify the old credentials are invalidated.
3. Set reviewed branch protection and least-privilege Actions permissions. Review anyone with workflow, administration, runner, environment or deployment access, including bypass rights. Pin third-party CI components to reviewed immutable revisions.
4. On a clean staged release, hash expected assets and compare the cPanel deployed PHP, static assets and relay configuration with an approved manifest. Inspect scheduled jobs, environment inheritance and webroot exceptions. CDN headers and an HTTP response cannot establish deployed source provenance.
5. Resolve the observed HTTP redirect from the HTTPS `/signoff/` route and verify the resulting canonical route, public cookie scope, strict transport policy, callback destinations and reverse-proxy trust.
